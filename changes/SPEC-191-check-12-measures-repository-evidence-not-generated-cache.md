## Objective

Define Repository Consistency Check 12's measurement population as the repository-candidate files Git already names — tracked files plus untracked non-ignored files — so that generated, ignored runtime artifacts regenerated by a mandatory `supabase db reset` are no longer judged as authored evidence, while the future-date invariant itself is left completely unchanged.

## Business Reason

DATABASE `-Finish` cannot currently reach `LOCAL_CERTIFY: READY` on any slice, which makes `Complete` unreachable for every remaining Batch-6 database slice including SPEC-190. The chain is reproduced end to end:

`Profiles()` returns `@($h|sort)`, so **DATABASE precedes REPOSITORY** → DATABASE's first mandatory command is `npx supabase db reset` → the reset regenerates the gitignored `supabase/.temp/pgdelta/*.json` catalog cache → that cache captures Supabase Realtime's own `realtime.messages_2026_09_16 … _2026_09_20` daily partition bounds, which are legitimately dated ahead because a partition must exist before the day it covers → Check 12 scans the cache and reports `FUTURE-DATED` → `check_repository_consistency.ps1` exits 1 → `Invoke-Verification` raises `MANDATORY_VERIFICATION_FAILED` → the receipt that `-Finish` deletes first is never rewritten → `COMPLETION_PREREQUISITE` refuses the `Complete` transition.

No ORVION migration creates those partitions; they belong to the Supabase platform stack. Deleting the cache first does not help, because the reset that regenerates it is itself one of the mandatory steps.

## Risks

- **The real risk is weakening a security-shaped guard, and the repair is deliberately shaped to avoid it.** Check 12's own comment records that it has *"NO exemption list, deliberately … every exemption is a place the next future date can hide."* This Change Request therefore adds no exemption, no pathname exception, no allowlist and no date-semantics change. It redefines only WHICH FILES the check measures, and it does so by adopting Git's existing definition rather than inventing one.
- **Under-measuring would be the dangerous failure.** Measured on the live tree, the population changes by exactly three files — `.claude/settings.json`, `.claude/settings.local.json`, `.orvion-local-certification.json` — plus `supabase/.temp/**` when present. Every one is declared by `.gitignore`'s own comments as machine-local or transient, and the receipt's entry says outright that it is *"an observation about a machine, never repository truth."* No authored evidence leaves the population.
- **A new authored file must not escape by being uncommitted.** `--others --exclude-standard` keeps untracked non-ignored files in the population, so a future-dated report is still flagged before it is ever `git add`ed. A dedicated control asserts this.
- **Git unavailability must not produce a vacuous green.** The repository's own standard is that *"a guard that asserts over an empty set is worse than one that fails."* If `git ls-files` yields nothing the check falls back to the current on-disk population, which over-measures rather than under-measures and therefore keeps failing closed.
- Not repairing blocks every remaining Batch-6 database slice, or forces an agent to delete the cache between two mandatory Finish steps — a silent workaround that would manufacture a green.

## Notes

**Why the population and not an exemption.** Check 12's own comment refuses an exemption list: *"every exemption is a place the next future date can hide."* A `pgdelta` pathname exception, a `.temp` exception or a future-date allowlist would each be exactly that, and each would have to be maintained by hand as the toolchain changes. Redefining the population is a different kind of change: it states what the check is FOR — evidence the repository authors — and then borrows the repository's existing, already-authoritative answer to "which files are those" instead of inventing a second one.

**Why `--cached --others --exclude-standard` rather than `git check-ignore`.** Both were measured against four fixtures in a throwaway Git repository, and on today's tree they agree — `git check-ignore` consults the index, so a tracked file is not reported as ignored even when a pattern matches it. The population form was chosen for three measured reasons rather than a semantic difference: it is ONE primitive that directly names the set, where the `check-ignore` form is a disk walk corrected by a second query (two authorities answering one question, the MEAS-1 shape this repository keeps finding); it costs one process invocation rather than one per candidate file; and it takes its answer from Git's own index rather than from whatever happens to be on disk. The tracked-then-ignored Boundary control is kept in the suite anyway, because it is the case that would separate the two if Git's semantics ever changed.

**Why this does not narrow `$allFiles`.** The shared collection also builds `$fileNames`, which Check 1 uses to resolve document and pgTAP filename references. Narrowing it globally would change which references resolve, and that effect has not been measured. The repair is therefore local to Check 12's own `$scan`, exactly as the defect is.

**Why Git is not a new dependency.** Check 12 already runs `& git -C $RepoRoot log -1 --format=%aI 2>$null` for its clock cross-check, a few lines below the line this Change Request replaces, and degrades silently when it returns nothing. The repair uses the same invocation shape and the same degradation posture.

**Why the existing nine assertions keep passing.** `Invoke-Guard` copies the repository into a temp directory that is NOT a Git repository, so `git ls-files` returns nothing there and the fallback population applies. Assertions 1–9 therefore continue to prove exactly what they proved before, now over the fallback path; the new git-backed section is what exercises the repaired path. That split is deliberate and is why both exist.

**This Change Request's own verification does not need a database.** Its Write Scope touches no `supabase/` path, so `Profiles()` derives CONTROL and REPOSITORY and not DATABASE — it can certify without running the reset whose output it exists to stop misreading. The DATABASE order is nevertheless reproduced by hand after implementation, because a unit-level green is what was insufficient the first time.
