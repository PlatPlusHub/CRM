## Objective

Make every tenant-scoped foreign key in ORVION tenant-qualified, so a row can only reference a parent belonging to the same tenant, enforced by the database rather than by whichever application layer remembered to check.

---

## Business Reason

Every tenant-scoped foreign key in the schema permitted a cross-tenant reference. Reproduced on the local database before any fix:

```
insert into bookings (tenant_id, customer_id, ...) values (TENANT_B, TENANT_A_CUSTOMER, ...);   -- ACCEPTED
select b.tenant_id, c.tenant_id from bookings b join customers c on c.id = b.customer_id;
  booking_tenant = bbbb…000b        customer_tenant = aaaa…000a
insert into leads (tenant_id, customer_id, ...) values (TENANT_B, TENANT_A_CUSTOMER, ...);      -- ACCEPTED
```

A single-column foreign key answers *"does this row exist?"* It does not answer *"does this row belong to me?"* RLS closes the read side, but its `WITH CHECK` validates only the new row's own `tenant_id` — nothing stopped a tenant from **writing** a reference across the boundary.

The result is not primarily a data leak; it is silent corruption. The child is visible to its owner while its parent is not, so ordinary joins drop rows, and `SECURITY DEFINER` paths — reporting views, integration RPCs — traverse a link that should not exist at all.

**Scale, measured rather than estimated: 189 single-column foreign keys, 50 child tables, 26 tenant-scoped parents, and zero composite tenant keys.** Every one of the 189 was exposed. This is a property of the whole schema, not of any one table — which is why it was fixed schema-wide rather than case by case.

This is also the defect that made SPEC-128's tenant-isolation criterion fail. Rather than special-casing that one column, the systemic cause was fixed.

---

## Risks

Moderate change volume, low change risk. All 72 tables hold zero rows, so this is pure DDL with nothing to validate or repair. The 216 statements were **generated by introspecting the live FK graph**, not written by hand, so no relationship is missed and none is transcribed wrongly.

Referential actions are carried across unchanged, preserving ADR-0007; the smoke-test's CHECK 7 re-verifies the Referential Action Standard afterwards and passes.

The semantics of `MATCH SIMPLE` (the PostgreSQL default) are load-bearing and correct here: the child's `tenant_id` is `NOT NULL` on all 50 tables while the referencing column is often nullable, and enforcement is skipped when any referencing column is NULL. An absent optional relationship therefore stays absent and unchecked; a present one must be same-tenant.

After go-live this change becomes materially harder: it would require validating every existing row and repairing whatever cross-tenant references had already been written — and those are unrepairable without knowing which tenant the row was meant for.

## Notes

**Approval basis.** Owner directive 2026-08-21, which lists "relationships that allow cross-tenant references" as an explicit audit target and makes "known tenant isolation weakness" a stop condition.

**How this was found.** Not by inspection — by a failing test. SPEC-128's tenant-isolation criterion failed, and rather than accepting the local explanation ("that column needs a tenant check"), the failure was generalised: *if this FK does not enforce tenant, which others do not?* The answer was all 189. The lesson is recorded because the method matters more than the instance: a single failing assertion was the thread that exposed a schema-wide defect.

**Why RLS was not sufficient, stated plainly for future readers.** RLS is a row-*visibility* mechanism. `USING` filters what you can see; `WITH CHECK` validates the row you are writing. Neither inspects the rows your foreign keys point at. Tenant isolation therefore needs both: RLS for visibility, and tenant-qualified foreign keys for referential integrity. ORVION had only the first.
