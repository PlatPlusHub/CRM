## 2. Google delivery — n8n workflow contract (build-ready spec)

One workflow, schedule-triggered (e.g. every 15 min). All DB calls use the `orvion_integration` Postgres credential; the whole pipeline is idempotent, so a crashed run is safely re-run.

1. **Map** — `select app.map_outcomes_to_conversions(500);` (advances the event cursor; returns rows mapped).
2. **Claim** — `select * from app.claim_conversion_deliveries('google_ads', 50);` → if 0 rows, stop. Only consent-granted conversions are ever returned (in-DB gate); each row carries `delivery_id`, conversion facts, click IDs (`gclid`/`gbraid`/`wbraid`), consent signals, and raw `customer_phone`/`customer_email`. **Delivery lease (SPEC-123, migration `202607050100`):** claiming opens a **30-minute lease**. Before it claims, this same call sweeps every `pending` delivery older than the lease into `failed` with a `LEASE_EXPIRED: …` reason and an `offline_conversion_failed` event flagged `expired_lease`, so a run that dies between Claim and Ack no longer strands its conversion forever — the standard retry path recovers it on a later run, consuming one of the five attempts. The workflow needs no node and no call for this; it is entirely database-side. See `§2a` items 4–6 for the three obligations this places on the workflow.
3. **Hash at the edge** (Function node) — normalize then SHA-256 (lowercase hex): email → trim + lowercase; phone → E.164 (`+…`) before hashing. **Raw PII never leaves n8n**; ORVION stores truth, Google receives hashes + click IDs only.
4. **Send** (HTTP node, OAuth2 credential with the `datamanager` scope) — Data Manager API conversion-event ingestion: click ID(s) + hashed `userIdentifiers` + `conversion_event_type_code`-mapped action + value/currency (revenue — never profit, ADR-0023) + `conversion_at` + consent (`adUserData`/`adPersonalization` from the claimed row). *Fast-moving surface:* verify the exact endpoint/payload field names against current Google Data Manager docs at build time (Learn-Before-Designing; the API is <1 yr old).
5. **Ack per row** — `select app.record_conversion_delivery_result(:delivery_id, :success, :response_json, :error_text);` → `sent`/`failed` + canonical events. Failed rows become re-claimable automatically on later runs (retry ceiling 5, then parked for review via `reporting`/events).

Monitoring: `offline_conversion_deliveries` rows + `offline_conversion_sent/failed` events are the health signal; a staleness/failure report is a Tier-A view away if operations wants one (Earn-It: build on demand).

### 2a. Build-spec corrections — MANDATORY, verified 2026-08-17 (read before building the workflow)

A pre-build review of the §2 contract against the actual migration source found three defects in the *draft node spec* (not in the §2 contract itself, and not in the database). SPEC-123's review added three more requirements (4–6) on 2026-08-20. Any session building this workflow must apply **all six**; building the naive spec would corrupt delivery state or silently inflate reported conversions.

1. **`validateOnly: true` must NEVER reach `Ack Result` as a success — VERIFIED BUG (severity: high).** `app.record_conversion_delivery_result(..., true, ...)` sets `delivery_status_code = 'sent'`, and `app.claim_conversion_deliveries` permanently excludes conversions holding a `pending` **or `sent`** delivery (migration `202607049200`, lines 145–149). A `validateOnly` request that returns HTTP 200 `{requestId}` proves only schema validity — **Google ingests nothing**. Acking it as success therefore marks a real conversion permanently delivered that was never delivered, with no path to re-claim it. **Rule: while `validateOnly` is true the workflow must either stop before `Ack Result`, or ack with `p_success = false` and an explicit `p_error` such as `'VALIDATE_ONLY_RUN — not a real delivery'`.** Flipping `validateOnly` to false and enabling the schedule must happen in the same change, never separately.
2. **Null `conversionValue`/`currency` must be omitted, not sent as JSON `null` — VERIFIED BUG (severity: medium).** `app.map_outcomes_to_conversions` sets conversion value/currency **only** for `payment_recorded` (migration `202607049300`, lines 93–94); `qualified_lead`, `booking_created`, and `ticket_issued` conversions therefore carry `conversion_value = NULL` and `currency_code = NULL` — i.e. 3 of the 4 mapper-produced event types. The `Hash At Edge` node must build the event object conditionally (add `conversionValue`/`currency` only when non-null) rather than emitting explicit nulls, which Google's API may reject.
3. **Phone hashing is a near-total no-op on current data — ARCHITECTURAL GAP, not a code bug.** Google requires E.164 before SHA-256, but `customers.primary_phone` is free text with no format constraint (migration `202607042100`, line 16) and no E.164 normalization exists anywhere in ORVION. Egyptian numbers stored locally (`01xxxxxxxxx`) cannot be converted without assuming a country code. The spec's normalizer correctly returns `null` rather than guess — but the consequence is that **phone identifiers will almost never be sent**, leaving email as the only user identifier and measurably weakening Google's match rate. Choosing a default-country-code policy is an owner/data decision, recorded as finding **PH8-3** in `MASTER_GAP_REGISTER.md`; it does not block the build.

4. **`transactionId` must be sent on every event — MANDATORY, added 2026-08-20 (finding PH8-5).** The `§2` payload carries no deduplication key. That was harmless while the only redelivery path was a *rejected* event, but SPEC-123's delivery lease (below) deliberately adds a second path: a run that crashes *after* Google ingests but *before* the ack has its delivery reclaimed and re-sent. Google deduplicates conversion events within a conversion action by `transactionId`, including across Data Manager API ingestion requests (verified 2026-08-20 against `developers.google.com/data-manager/api/devguides/events/send-events` and `support.google.com/google-ads/answer/6386790`). **Rule: set `transactionId` to the row's `conversion_id`** — the `offline_conversions.id` UUID, already returned by `app.claim_conversion_deliveries`, stable and immutable across every retry and reclaim. Without it, at-least-once delivery silently inflates reported conversions and feeds that inflation to Smart Bidding. Verify the exact field name against current Google docs at build time, as `§2` already requires for the rest of the payload.
5. **The workflow must set its own `Timeout Workflow` = 10 minutes — MANDATORY, added 2026-08-20 (SPEC-123).** The database lease that recovers stranded deliveries is 30 minutes, derived as 3x this timeout; the safety invariant is **lease > workflow timeout > worst-case run duration**. n8n Cloud's own maximum execution time is plan-dependent (n8n docs, verified 2026-08-20), so it must not be relied on as the bound. If the schedule, the batch size, or this timeout ever changes, the lease in `app.claim_conversion_deliveries` must be revisited in the same change.
6. **A late ack now raises, by design — added 2026-08-20 (SPEC-123).** If a run resumes after its lease expired and calls `app.record_conversion_delivery_result` on a reclaimed delivery, the RPC raises (`delivery … is retried|failed — only pending deliveries can be resolved`). That is the protection that stops a lost-lease run from marking a conversion `sent`; the workflow must treat it as an expected, non-fatal outcome for that row and must not retry it as a new delivery.
