### DC-1 / R7 — Money precision
- **Root cause:** money type chosen (`numeric(14,2)`) before the multi-currency reference model (`currencies.decimal_places`) was reconciled with storage scale; no test asserts scale ≥ currency precision. **Why missed:** all prior reviews checked table/column existence, never scale.
- **Business:** financial inaccuracy/un-reconcilable balances in GCC/Umrah/Hajj (KWD/BHD/OMR/JOD = 3-dp). **Technical:** truncation on write; the 3 derived RPCs inherit it. **Architectural:** money is cross-cutting to finance/booking/marketing.
- **Affected — tables:** all 22+ money columns (invoices, payments, refunds, payment_allocations, journal_entry_lines, booking_items, quotation_items, campaign_daily_metrics, offline_conversions, chart_of_accounts opening, exchange_rate_adjustments, subscription/plan amounts). **RPCs:** customer_balance, supplier_balance, booking_item_profit, all finance write RPCs. **Events:** none. **Catalogs:** none. **Permissions:** none. **Reports/dashboards:** all finance. **ADR:** amend/append (money-storage standard). **Canon:** `30` conventions, `31` schema. **Roadmap:** Batch 0.
- **Migration:** yes (ALTER TYPE scale). **Additive?** No — modifies built columns; must precede finance data. **Order:** Batch 0, after pgTAP (DC-16). **Design:** `numeric(19,4)` + rounding via `currencies.decimal_places`. **Req/Opt:** R.

### DC-2 — Write idempotency
- **Root cause:** RPCs designed for authorization/state-correctness, not client-retry semantics; idempotency solved only at integration edges. **Business:** duplicate payments/bookings/invoices on retry. **Technical:** no dedup on inbound writes. **Affected:** new `idempotency_keys` table; optional param on mutating RPCs; no catalog/event/permission. **Migration:** additive. **Order:** Batch 1 (with first client). **Req:** R.

### DC-3 — Concurrency control
- **Root cause:** CHECK constraints mistaken for concurrency guarantees; no locking discipline documented. **Business:** oversold departures/allotments; lost updates. **Affected:** hold/issue RPCs (FOR UPDATE / advisory locks); optional `row_version` pattern; inventory tables (CDD-2). **Migration:** additive (logic + optional column). **Order:** Batch 1, before inventory ships. **Req:** R.

### DC-4 — PII erasure boundary

### PH8-1 — A `pending` delivery is unrecoverable (discovered + source-verified 2026-08-17, Phase-8 pre-build workflow review)
- **Evidence (source-verified against migration `202607049200_offline_conversion_core.sql`):** `app.claim_conversion_deliveries` excludes any conversion holding a delivery whose `delivery_status_code in ('pending','sent')` (lines 145–149), and `app.record_conversion_delivery_result` raises unless the delivery is currently `pending` (lines 217–220). The retry design therefore recovers `failed` deliveries only — a `failed` row is retired to `retried` and a fresh attempt is opened on the next claim (lines 157–165). A row that is claimed but never acked stays `pending` forever. Verified by grep that **no** stale/timeout/reaper logic exists anywhere in `supabase/migrations/**`.
- **Why it matters:** the outbox is designed for a stateless caller (ADR-0023) that can crash. Any n8n run interrupted between `Claim Deliveries` and `Ack Result` — deploy, timeout, OAuth expiry mid-run, rate-limit abort, n8n incident — permanently strands that conversion: it is never re-claimed, never retried, never acked, and never counted as failed. It is invisible to the retry ceiling because the ceiling counts delivery rows, not outcomes. Silent, unbounded revenue-attribution loss with no operator signal.
- **Not a Phase-8 blocker for a supervised manual run** (an operator watching one execution can see the interruption), but it must be resolved before the workflow is activated on its 15-minute schedule and left unattended.
- **RESOLVED 2026-08-20 — owner-approved lease / visibility timeout (SPEC-123, migration `202607050100`).** `app.claim_conversion_deliveries` now terminalizes every `pending` delivery older than a **30-minute lease** to `failed` (stamped `LEASE_EXPIRED: …`, emitting `offline_conversion_failed` with payload `expired_lease: true`) before it claims, so the existing retry machinery recovers the conversion unchanged. Chosen over a separate `requeue_stale_*` RPC because the sweep needs no orchestration, so the `§2` workflow contract stays exactly 7 nodes. No schema change and no new status vocabulary — `failed` already exists in the `offline_conversion_delivery_status` catalog; `created_at` is the lease start (the row is INSERTed at claim time), so no column was added. Expired attempts **count toward the ceiling of 5**, so a crashed worker consumes an attempt and cannot bypass the limit; a ceiling-exhausted expired lease terminalizes to `failed` rather than looking in-flight forever; a `sent` delivery is never touched; and a late "zombie" ack is refused by the unchanged `record_conversion_delivery_result`. **Lease derivation (not arbitrary): lease > enforced workflow timeout > worst-case run** — 30 min is 3x the 10-minute `Timeout Workflow` the workflow is now required to set, and 6x the ~5-minute worst-case 50-row run; recovery latency is at most the lease plus one 15-minute tick. Full reasoning, the live two-session concurrency proofs, and the index measurement: `changes/SPEC-123-conversion-delivery-lease.md`. Permanent guard: `supabase/tests/09_conversion_delivery_lease_test.sql` (17 assertions). **Deployed to Primary 2026-08-20 and verified live there** — 90 migrations, the deployed function behaviorally exercised. It was also applied to Secondary that day under the dual-deployment rule since **permanently revoked** (owner-ratified 2026-08-20: `PlatPlusHub/CRM` → Primary only); that apply was **fully reverted on Secondary and verified**, so **PH8-1 is resolved on Primary only — which is correct, because Primary is the sole CRM environment** (`MASTER_INTEGRATION_CATALOG.md §0/§4`).
- **Residual, deliberately not absorbed into SPEC-123:** the lease converts *silent permanent loss* into *at-least-once delivery*, opening a narrow double-count window (crash after Google ingests but before the ack). The mitigation is workflow-side, not database-side — see **PH8-5**. Also unchanged: a conversion whose runs crash five times is now visibly `failed` instead of invisibly `pending`, but is still undelivered, and no delivery-health surface exists for an operator to notice it (**PH8-2** owns that observability gap).

### PH8-5 — No deduplication key is sent to Google; the PH8-1 lease makes double-counting possible (discovered 2026-08-20, SPEC-123 three-perspective review)
- **Evidence (source-verified + external):** the `§2` send step (step 4) builds the Data Manager payload from click IDs, hashed `userIdentifiers`, action, value/currency, `conversion_at` and consent — **no transaction/order identifier**. Google's own documentation is explicit that `transactionId` is the deduplication key: *within the same conversion action, Google Ads uses the `transactionId` to deduplicate conversion events sent from different sources, including Data Manager API ingestion requests* (`developers.google.com/data-manager/api/devguides/events/send-events`; `support.google.com/google-ads/answer/6386790`, verified 2026-08-20).
- **Why it matters, and why it is new:** before SPEC-123, a redelivery could only follow a `failed` ack — i.e. Google had rejected the event and ingested nothing, so retrying was safe. The lease deliberately introduces a second redelivery path: a run that crashes *after* Google ingests the event but *before* the ack now has its delivery reclaimed and re-sent. That is the correct trade (at-least-once beats silent permanent loss) but it is only *safe* if Google can deduplicate, and today it cannot. The failure is silent and inflates reported conversions, which then feeds Smart Bidding.
- **Fix (no ORVION code change required):** send `offline_conversions.id` as `transactionId` on every event. It is already a stable, unique, immutable per-conversion UUID that survives every retry and reclaim, and `app.claim_conversion_deliveries` already returns it as `conversion_id`. This is a **workflow-side** change, recorded as mandatory build-spec correction 4 in `MASTER_INTEGRATION_CATALOG.md §2a`; verify the exact field name against current Google docs at build time, as `§2` already requires for the rest of the payload.
- **Status:** nothing is broken today — the workflow does not exist yet, and no conversion has ever been delivered. This must be applied when the workflow is built, before `validateOnly` is ever flipped to false.

### DEL-1 — the database cannot destroy a storage object (discovered 2026-08-27, WP-04-D, live-verified on Primary and local)
- **Category:** platform capability · **Severity:** High (it bounds the whole retention design) · **Status:** BLOCKED — MISSING PLATFORM CAPABILITY · **Owner:** engineering (WP-04-E)
- **Evidence (live, both environments):** `storage.protect_delete()` is installed by Supabase as a `BEFORE DELETE` trigger on **both** `storage.objects` and `storage.buckets`, raising `42501` — *"Direct deletion from storage tables is not allowed. Use the Storage API instead."* — unless the session GUC `storage.allow_delete_query` is `'true'`; its own `HINT` states the reason: *"This prevents accidental data loss from orphaned objects."* Independently, `pg_net` is **not** in `pg_extension` on either environment (`moddatetime`, `pg_cron`, `pg_stat_statements`, `pgcrypto`, `supabase_vault`, `uuid-ossp`, `plpgsql`, plus `pgtap` locally), so the database cannot reach the Storage HTTP API either. Pinned by assertion 12 of `49_document_retention_test.sql`.
- **Root cause:** object bytes live in S3, not in PostgreSQL. `storage.objects` is only the index of them, and Supabase deliberately prevents that index being edited out from under the bytes.

### RBAC-1 — every privilege grant made outside one RPC was unaudited, and no revocation was ever audited (discovered + FIXED 2026-08-27, `202607055100`)
- **Category:** security / audit integrity · **Severity:** High · **Status:** FIXED · **Owner:** engineering
- **Evidence (live):** `public.user_role_assignments` carried **no triggers whatsoever** — `pg_trigger` returned zero non-internal rows for it. `role_assigned` was emitted only by `app.assign_user_role`; `role_removed` was a registered event type with no producer anywhere; no `app.revoke_user_role` existed. The table's RLS (`scope_insert`/`scope_update`/`scope_delete`) checks `app.has_permission('MANAGE_USERS')`, while the RPC charges `app.authorize`, which additionally composes MFA.
- **Impact:** (1) no privilege revocation in ORVION's history was ever recorded — an administrator's session could strip a colleague's roles, including the Owner's, and leave the `security`-severity audit stream looking untouched; (2) direct-DML **grants** were equally unrecorded, so grant coverage was never complete either; (3) the destructive path cost no step-up while the safe path did, inverting the incentive the control exists to create.
- **Root cause:** the rule lived in a caller rather than on the table — the WP-00 class this programme has closed repeatedly elsewhere.
- **Remediation (applied):** one `AFTER INSERT OR UPDATE OR DELETE` trigger, `app.emit_role_change()`, is now the **single producer** of both events on every path; `app.assign_user_role` **lost** its own `record_event` call rather than gaining a duplicate beside the trigger's. Session-ful writes are charged `app.authorize('MANAGE_USERS')` (MFA parity); session-less platform paths are exempt from the *check* and never from the *record*. Only a change in **effective access** is audited (`is_active` **and** `ends_at`, since either alone ends a grant), so column churn does not pollute the stream. `app.revoke_user_role()` added — it ends the assignment rather than deleting it, since `24_assignment_history_test.sql` establishes assignment history as evidence.
- **Test requirement (met):** `51_role_change_audit_test.sql` (13) — direct-DML grant audited, RPC emits exactly one, both revocation routes audited, no-op emits nothing, MFA denial **with** its positive control, system path permitted and still audited with no invented actor.
