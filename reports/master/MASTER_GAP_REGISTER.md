### DC-1 / R7 — Money precision
- **Root cause:** money type chosen (`numeric(14,2)`) before the multi-currency reference model (`currencies.decimal_places`) was reconciled with storage scale; no test asserts scale ≥ currency precision. **Why missed:** all prior reviews checked table/column existence, never scale.
- **Business:** financial inaccuracy/un-reconcilable balances in GCC/Umrah/Hajj (KWD/BHD/OMR/JOD = 3-dp). **Technical:** truncation on write; the 3 derived RPCs inherit it. **Architectural:** money is cross-cutting to finance/booking/marketing.
- **Affected — tables:** all 22+ money columns (invoices, payments, refunds, payment_allocations, journal_entry_lines, booking_items, quotation_items, campaign_daily_metrics, offline_conversions, chart_of_accounts opening, exchange_rate_adjustments, subscription/plan amounts). **RPCs:** customer_balance, supplier_balance, booking_item_profit, all finance write RPCs. **Events:** none. **Catalogs:** none. **Permissions:** none. **Reports/dashboards:** all finance. **ADR:** amend/append (money-storage standard). **Canon:** `30` conventions, `31` schema. **Roadmap:** Batch 0.
- **Migration:** yes (ALTER TYPE scale). **Additive?** No — modifies built columns; must precede finance data. **Order:** Batch 0, after pgTAP (DC-16). **Design:** `numeric(19,4)` + rounding via `currencies.decimal_places`. **Req/Opt:** R.

### DC-2 — Write idempotency
- **Root cause:** RPCs designed for authorization/state-correctness, not client-retry semantics; idempotency solved only at integration edges. **Business:** duplicate payments/bookings/invoices on retry. **Technical:** no dedup on inbound writes. **Affected:** new `idempotency_keys` table; optional param on mutating RPCs; no catalog/event/permission. **Migration:** additive. **Order:** Batch 1 (with first client). **Req:** R.

### DC-3 — Concurrency control
- **Root cause:** CHECK constraints mistaken for concurrency guarantees; no locking discipline documented. **Business:** oversold departures/allotments; lost updates. **Affected:** hold/issue RPCs (FOR UPDATE / advisory locks); optional `row_version` pattern; inventory tables (CDD-2). **Migration:** additive (logic + optional column). **Order:** Batch 1, before inventory ships. **Req:** R.

### DC-4 — PII erasure boundary

### PH8-1 — A `pending` delivery is unrecoverable (discovered + source-verified 2026-08-17, Phase-8 pre-build workflow review)
- **Evidence (source-verified against migration `202607049200_offline_conversion_core.sql`):** `app.claim_conversion_deliveries` excludes any conversion holding a delivery whose `delivery_status_code in ('pending','sent')` (lines 145–149), and `app.record_conversion_delivery_result` raises unless the delivery is currently `pending` (lines 217–220). The retry design therefore recovers `failed` deliveries only — a `failed` row is retired to `retried` and a fresh attempt is opened on the next claim (lines 157–165). A row that is claimed but never acked stays `pending` forever. Verified by grep that **no** stale/timeout/reaper logic exists anywhere in `supabase/migrations/**`.
- **Why it matters:** the outbox is designed for a stateless caller (ADR-0023) that can crash. Any n8n run interrupted between `Claim Deliveries` and `Ack Result` — deploy, timeout, OAuth expiry mid-run, rate-limit abort, n8n incident — permanently strands that conversion: it is never re-claimed, never retried, never acked, and never counted as failed. It is invisible to the retry ceiling because the ceiling counts delivery rows, not outcomes. Silent, unbounded revenue-attribution loss with no operator signal.
- **Not a Phase-8 blocker for a supervised manual run** (an operator watching one execution can see the interruption), but it must be resolved before the workflow is activated on its 15-minute schedule and left unattended.
- **RESOLVED 2026-08-20 — owner-approved lease / visibility timeout (SPEC-123, migration `202607050100`).** `app.claim_conversion_deliveries` now terminalizes every `pending` delivery older than a **30-minute lease** to `failed` (stamped `LEASE_EXPIRED: …`, emitting `offline_conversion_failed` with payload `expired_lease: true`) before it claims, so the existing retry machinery recovers the conversion unchanged. Chosen over a separate `requeue_stale_*` RPC because the sweep needs no orchestration, so the `§2` workflow contract stays exactly 7 nodes. No schema change and no new status vocabulary — `failed` already exists in the `offline_conversion_delivery_status` catalog; `created_at` is the lease start (the row is INSERTed at claim time), so no column was added. Expired attempts **count toward the ceiling of 5**, so a crashed worker consumes an attempt and cannot bypass the limit; a ceiling-exhausted expired lease terminalizes to `failed` rather than looking in-flight forever; a `sent` delivery is never touched; and a late "zombie" ack is refused by the unchanged `record_conversion_delivery_result`. **Lease derivation (not arbitrary): lease > enforced workflow timeout > worst-case run** — 30 min is 3x the 10-minute `Timeout Workflow` the workflow is now required to set, and 6x the ~5-minute worst-case 50-row run; recovery latency is at most the lease plus one 15-minute tick. Full reasoning, the live two-session concurrency proofs, and the index measurement: `changes/SPEC-123-conversion-delivery-lease.md`. Permanent guard: `supabase/tests/09_conversion_delivery_lease_test.sql` (17 assertions). **Deployed to Primary 2026-08-20 and verified live there** — 90 migrations, the deployed function behaviorally exercised. It was also applied to Secondary that day under the dual-deployment rule since **permanently revoked** (owner-ratified 2026-08-20: `PlatPlusHub/CRM` → Primary only); that apply was **fully reverted on Secondary and verified**, so **PH8-1 is resolved on Primary only — which is correct, because Primary is the sole CRM environment** (`MASTER_INTEGRATION_CATALOG.md §0/§4`).
- **Residual, deliberately not absorbed into SPEC-123:** the lease converts *silent permanent loss* into *at-least-once delivery*, opening a narrow double-count window (crash after Google ingests but before the ack). The mitigation is workflow-side, not database-side — see **PH8-5**. Also unchanged: a conversion whose runs crash five times is now visibly `failed` instead of invisibly `pending`, but is still undelivered, and no delivery-health surface exists for an operator to notice it (**PH8-2** owns that observability gap).

### PH8-5 — No deduplication key is sent to Google; the PH8-1 lease makes double-counting possible (discovered 2026-08-20, SPEC-123 three-perspective review)
- **Evidence (source-verified + external):** the `§2` send step (step 4) builds the Data Manager payload from click IDs, hashed `userIdentifiers`, action, value/currency, `conversion_at` and consent — **no transaction/order identifier**. Google's own documentation is explicit that `transactionId` is the deduplication key: *within the same conversion action, Google Ads uses the `transactionId` to deduplicate conversion events sent from different sources, including Data Manager API ingestion requests* (`developers.google.com/data-manager/api/devguides/events/send-events`; `support.google.com/google-ads/answer/6386790`, verified 2026-08-20).
- **Why it matters, and why it is new:** before SPEC-123, a redelivery could only follow a `failed` ack — i.e. Google had rejected the event and ingested nothing, so retrying was safe. The lease deliberately introduces a second redelivery path: a run that crashes *after* Google ingests the event but *before* the ack now has its delivery reclaimed and re-sent. That is the correct trade (at-least-once beats silent permanent loss) but it is only *safe* if Google can deduplicate, and today it cannot. The failure is silent and inflates reported conversions, which then feeds Smart Bidding.
- **Fix (no ORVION code change required):** send `offline_conversions.id` as `transactionId` on every event. It is already a stable, unique, immutable per-conversion UUID that survives every retry and reclaim, and `app.claim_conversion_deliveries` already returns it as `conversion_id`. This is a **workflow-side** change, recorded as mandatory build-spec correction 4 in `MASTER_INTEGRATION_CATALOG.md §2a`; verify the exact field name against current Google docs at build time, as `§2` already requires for the rest of the payload.
- **Status:** nothing is broken today — the workflow does not exist yet, and no conversion has ever been delivered. This must be applied when the workflow is built, before `validateOnly` is ever flipped to false.

### DEL-1 — the database cannot destroy a storage object (discovered 2026-08-27, WP-04-D, live-verified on Primary and local)
- **Category:** platform capability · **Severity:** High (it bounds the whole retention design) · **Status:** BLOCKED — MISSING PLATFORM CAPABILITY · **Owner:** engineering (WP-04-E)
- **Evidence (live, both environments):** `storage.protect_delete()` is installed by Supabase as a `BEFORE DELETE` trigger on **both** `storage.objects` and `storage.buckets`, raising `42501` — *"Direct deletion from storage tables is not allowed. Use the Storage API instead."* — unless the session GUC `storage.allow_delete_query` is `'true'`; its own `HINT` states the reason: *"This prevents accidental data loss from orphaned objects."* Independently, `pg_net` is **not** in `pg_extension` on either environment (`moddatetime`, `pg_cron`, `pg_stat_statements`, `pgcrypto`, `supabase_vault`, `uuid-ossp`, `plpgsql`, plus `pgtap` locally), so the database cannot reach the Storage HTTP API either. Pinned by assertion 12 of `49_document_retention_test.sql`.
- **Root cause:** object bytes live in S3, not in PostgreSQL. `storage.objects` is only the index of them, and Supabase deliberately prevents that index being edited out from under the bytes.

### RBAC-1 — every privilege grant made outside one RPC was unaudited, and no revocation was ever audited (discovered + FIXED 2026-08-27, `202607055100`)
- **Category:** security / audit integrity · **Severity:** High · **Status:** FIXED · **Owner:** engineering
- **Evidence (live):** `public.user_role_assignments` carried **no triggers whatsoever** — `pg_trigger` returned zero non-internal rows for it. `role_assigned` was emitted only by `app.assign_user_role`; `role_removed` was a registered event type with no producer anywhere; no `app.revoke_user_role` existed. - **Evidence:** every status transition's required permission is stated twice — as an inline `VALUES` list inside each `app.advance_*` function (which also carries the EVENT code), and as a row in `app.status_transitions` (which `app.enforce_status_transition`, the BEFORE UPDATE trigger on every status-bearing table, actually reads). - **Impact, demonstrated rather than theorised:** the TASK-1 fix changed only the function. The employee was **still** refused `permission denied: ASSIGN_TASK`, because the trigger reads the table — and the two sources were now in live disagreement. ### RLS-1 — a read permission confers write authority on eleven tables (discovered 2026-08-28, Phase C policy sweep) — **MERGED into SEC-1 2026-08-28; see the closure record at the end of this file**
- **Category:** authorization model / misleading contract · **Severity:** Medium · **Status:** OBSOLETE (merged into SEC-1) · **Owner:** —
- **Evidence:** `bookings`, `booking_items`, `leads`, `quotations`, `tasks`, `documents`, `document_links`, `complaints`, `conversations`, `customer_notes` and `service_requests` each carry a single `for ALL` policy whose `USING` and `WITH CHECK` are identical and both include `app.has_tenant_wide_read()`, which is `app.has_permission('VIEW_ALL_BRANCHES')`.
- **Impact — stated precisely, because the distinction matters:** **not exploitable today.** Only `owner` and `ceo` hold `VIEW_ALL_BRANCHES`, and both already hold every relevant write permission, so nobody gains anything they did not have. The defect is **latent**: the day any read-oriented role (a read-only auditor, a reporting account, or `system_administrator`, which today holds no permissions at all) is granted `VIEW_ALL_BRANCHES`, it silently acquires INSERT and UPDATE on eleven tables — a defect that arrives without anyone editing a policy.
- **Root cause:** a `for ALL` policy uses one expression for reading and writing, and the expression chosen names the read concept.
- **Remediation:** introduce `app.has_tenant_wide_write()` (identical membership today) and use it in `WITH CHECK`, so the two concepts are separable the day they diverge. Behaviour-preserving. Scoped as its own package because it touches the most heavily tested policies in the system and deserves a full cross-path re-verification rather than a session-end edit.
- **Test requirement:** a fixture role holding only `VIEW_ALL_BRANCHES` must be refused INSERT and UPDATE on all eleven tables, with owner as the positive control.

### ATTR-1 — `created_by` was a caller-supplied column on twenty tables (discovered + FIXED 2026-08-28, `202607056400`)
- **Category:** audit integrity / authorization · **Severity:** Medium–High · **Status:** FIXED · **Owner:** engineering
- **Evidence:** a sweep of every table `authenticated` may INSERT for columns naming an actor found that `archived_by` (10 tables), `document_versions.uploaded_by` and `approval_requests.requested_by` are already derived by triggers — and that **`created_by` was not, on twenty tables**: bookings, booking_items, customers, customer_notes, leads, quotations, invoices, payments, payment_allocations, receipts, refunds, journal_entries, documents, document_links, complaints, service_requests, tasks, catalog_values, exchange_rate_adjustments, user_branch_assignments.
- **Root cause:** every `app.*` RPC sets it from the session; direct DML did not have to. This is FIN-4's defect — the same shape, the same principle — recurring across a class instead of one column, and it was found by sweeping for the class rather than by tripping over an instance.
- **Impact:** any tenant user could create a customer, booking, invoice or payment **attributed to a colleague**, corrupting exactly the attribution an audit trail exists to carry. Not cross-tenant — RLS holds that boundary. On `documents` it is worse than misleading: `scope_isolation` reads `created_by = current_user_id()` as one of its **visibility grants**, so there the column is load-bearing for authorization.
- **Remediation (applied):** `app.derive_created_by()`, a BEFORE INSERT OR UPDATE trigger on all twenty tables, following WP-00's shape — DERIVE, DO NOT VALIDATE — so the forgery is unrepresentable rather than merely refused. **Immutable on UPDATE**, because deriving only on INSERT would leave the value editable a moment later; safe because **no `app.*` or `public.*` function updates the column**, verified against every function body before the trigger was written. Session-less platform paths keep the attribution they set.
- **Deliberately NOT included, and recorded rather than guessed — ATTR-2:** `invoices.voided_by`, `journal_entries.voided_by`, `approval_requests.reviewed_by`, `subscription_payment_proofs.reviewed_by` / `uploaded_by`. Those are ACTION attributions, stamped when the action happens rather than when the row is created, so an insert-time derivation would be wrong for them. They need the same treatment at the moment of the action — a different trigger shape, and a separate package.
- **Test requirement (met):** `61_created_by_is_derived_test.sql` (8) — the employee CAN write the row (so the assertion is about attribution, not permission) while naming a colleague, and the row is attributed to the actual author; the value proven immutable on UPDATE; `documents` proven separately because there it is an authorization value; the session-less path proven to keep its own attribution; and **the class pinned** — every insertable table with a `created_by` column must carry the trigger, so a table added later without one fails the suite.

### SLA-1 — the manager escalation canon makes MANDATORY had never fired (discovered + FIXED 2026-08-29, `202607056600`)
- **Category:** operational completeness / canon compliance · **Severity:** High · **Status:** FIXED · **Owner:** engineering
- **The canonical requirement, quoted rather than inferred.** canon 04 § SLA Escalation Rule: *"If a lead is not responded to within 15 minutes: Notify the assigned employee. **Notify the employee's manager.** Record an escalation event."* canon 10 § Lead Notifications repeats it and adds the second step: *"After another 15 minutes without response: Notify reassigned employee. **Notify manager.** Record reassignment event."* canon 10 also lists **"Manager escalation" among the notifications a user CANNOT MUTE** — mandatory operational behaviour, not a preference. The 15/30-minute windows already matched `app.process_lead_sla`'s defaults, so no timing was invented here either.
- **Evidence (reproduced before fixing, with a positive control).** Standard configuration — an employee, a `branch_manager` and a `department_manager`, all placed in the branch/department through `user_branch_assignments`, all holding TENANT-scoped roles, which is exactly what `app.assign_user_role` produces (`p_scope_type` defaults to `'tenant'`, leaving `branch_id`/`department_id` NULL). One SLA pass produced: employee **1** notification, branch manager **0**, department manager **0** — while a positive control in the same transaction proved the managers **can see the lead** (RLS returns it). A notification failure, not an unreachable row.
- **Root cause — the recurring shape, this time in the operational layer rather than a guard.** The manager lookup asked `(ura.branch_id = r.branch_id or ura.department_id = r.department_id)` of `user_role_assignments` ALONE. ORVION's authoritative definition of governance is `app.visible_branch_ids()` / `app.visible_department_ids()`, each a **UNION** of tenant-wide read, the user's `user_branch_assignments` **placement**, and scoped `user_role_assignments`. The SLA lookup used only the third — the one that is NULL for every role assignment ORVION's own RPC creates by default. **Two definitions of one concept, and the narrower one sat in the place that mattered.**
- **Second instance, same defect:** the reassignment branch notified only the NEW assignee. Canon 10 requires the manager to be told there too, and that branch had **no manager notification at all** — not mis-scoped, simply never written.
- **Why no existing test caught it:** `34_event_write_path_test` and `36_subscription_gate_system_paths_test` both exercise `process_lead_sla`, but they assert the system-path survival and the subscription-gate isolation — that the *event* is emitted for the right tenant. **Neither asserts who is notified.** This was a genuinely uncovered canonical requirement rather than a guard that lied.
- **Remediation (applied):** `app.lead_responsible_managers(tenant, branch, department, exclude_user)` holds the scope rule ONCE and is used by BOTH paths, because a second copy of a predicate is what produced the defect. It mirrors `visible_branch_ids`/`visible_department_ids` for an arbitrary user (those read the session; this runs with none), and adds the `is_active` / `starts_at` / `ends_at` bounds the authoritative functions apply, which the old inline predicate omitted (SPEC-148: revocation is complete). The tenant-wide-read source is deliberately absent — it resolves to ceo/owner, who are not in canon's escalation path.
- **Deliberately NOT changed:** which roles escalate (still `branch_manager` / `department_manager` — widening to ceo/owner would be new policy); the 15/30 windows; the warn-before-reassign ordering; the qualifying-interaction definition; the round-robin choice of the next assignee; the subscription-gate skip; the event vocabulary; the immutability of assignment history.
- **Test requirement (met):** `63_sla_escalation_test.sql` (11) — a positive control proving the manager can SEE the lead; both managers notified on warning; **a negative control proving a `branch_manager` who governs ANOTHER branch is still NOT notified**, so the scope test was widened rather than removed; one event, not one per notification; a second pass warning nothing, so managers are not spammed every minute; and both halves of the reassignment notification.
- **A correction to my own first version of that test:** it passed assertion 10 **for the wrong reason.** The reassignment pool includes the managers, the tie broke on `u.id asc`, and the branch manager's own *"reassigned to you"* notice was being counted as a manager escalation. The fixture now pins the round robin to the colleague and asserts the new assignee explicitly, so the two cannot overlap. Recorded because it is exactly the vacuous-assertion shape this programme exists to catch.

### LEAD-3 — the SLA reassignment pool includes managers (discovered 2026-08-29)
- **Category:** operational policy · **Severity:** Low–Medium · **Status:** BLOCKED — BUSINESS DECISION · **Owner:** owner
- **Evidence (observed while proving SLA-1, not theorised):** `app.process_lead_sla`'s candidate query is *everyone placed in the lead's branch and department* who is active and is not the current assignee, ordered by least-recently-assigned then `u.id`. Managers are placed there too, so they are candidates — and in a team where nobody has held a lead yet, every `last_at` is NULL and the tie breaks on `u.id`, which handed the lead to the **branch manager** in a clean fixture.
- **Impact:** an overdue lead can be auto-assigned to a manager rather than to a front-line handler. Not a security issue — a `branch_manager` holds `ASSIGN_LEAD` and `VIEW_BRANCH_DATA` and can legitimately work the lead — but it changes who carries operational load, and it makes the escalation target and the work target the same person.
- **Why it is not decidable from evidence:** canon 04 says *"Reassign the lead to another **eligible employee**"* and defines neither "eligible" nor whether a manager qualifies. Both readings are defensible: loosely, any staff member placed in that team; strictly, a front-line lead-handling role, with the manager as escalation target rather than next handler.
- **Decision required:** whether the pool is filtered by role (and to which roles), whether managers are a last resort when no employee is available, and whether the `u.id` tie-break should instead be deterministic on something operational (e.g. current open-lead count).
- **Deliberately NOT changed:** this is pre-existing behaviour and `202607056600` is about who is NOTIFIED, not who receives the work. Conflating the two would have shipped an unrequested policy change inside a defect fix.

### SCHED-1 (INVESTIGATED + PARTIALLY ADDRESSED 2026-08-28, `202607056300`) — nothing invokes the storage executor
- **Category:** operations / scheduling · **Severity:** Medium · **Status:** BLOCKED — EXTERNAL DEPENDENCY (one owner-placed secret) + ARCHITECTURAL DECISION (which route) · **Owner:** owner
- **What actually needs scheduling, measured live:** three of the four recurring jobs already have pg_cron entries on Primary — `app.reconcile_document_storage` (daily 00:30), `app.process_lead_sla` (every minute), `app.process_subscription_lifecycle` (daily 00:10). The **storage executor** is the fourth and has no scheduler at all. It is an Edge Function (ACTIVE, `verify_jwt = true`), proven end to end by `scripts/verify_storage_end_to_end.ps1` — except that nothing ever calls it.
- **The three routes, costed on live evidence rather than preference:**
  - **A. pg_cron + pg_net + Vault.** `pg_cron` 1.6.4 is installed, `pg_net` 0.20.4 is available but NOT installed, and **`supabase_vault` IS installed** — which materially improves the position recorded when pg_net was first declined, because the invocation secret could live encrypted in Vault instead of in a migration, a column or a log. The cost is still real: installing pg_net gives the DATABASE outbound HTTP, a capability ORVION does not have today.
  - **B. n8n schedule → HTTP request.** n8n is live (0 workflows, 2 credentials, re-proven 2026-08-28) and keeps outbound HTTP out of the database, at the cost of making a core retention path depend on n8n's uptime.

If the executor never runs — or is scheduled and then breaks — retention-expired findings accumulate, bytes ORVION undertook to destroy stay on disk, and nothing says so. `app.storage_action_backlog()` (and its `public` wrapper, service_role only) reports pending actions, **the age of the oldest**, how many have already failed an attempt, the last attempt time, and the wider unresolved-finding count. Plus 4 HTTP assertions in `verify_storage_end_to_end.ps1`, including the same monitor-equals-worker check over the wire.

### TRANS-2 — eight lead transitions were enforced for sequence and not for authority (discovered + FIXED 2026-08-28, `202607056200`)
- **Category:** authorization / lifecycle · **Severity:** High · **Status:** FIXED · **Owner:** engineering
- **Evidence:** `app.status_transitions` is the direct-DML half of transition authority, read by `app.enforce_status_transition`, and its only authorization column is `permission_key` — applied `if v_permission is not null`. Eight `leads` rows carry NULL: `assigned->contacted`, `contacted->qualified`, `qualified->quotation_sent`, `qualified->won`, `quotation_sent->negotiation`, `quotation_sent->won`, `negotiation->won`, `won->converted`.
- **Root cause:** the rule those transitions actually carry — *"the assigned handler, or ASSIGN_LEAD, plus MFA"*, stated verbatim by `app.advance_lead`, `app.convert_lead` and `app.record_lead_interaction` — has **no column that can express it**. A null therefore meant "no check at all" on the direct path while the RPCs refused anyone who was not the handler.
- **Impact:** direct DML could walk a COLLEAGUE'S lead from `contacted` to `won` and on to `converted` with no capability check. Reachable: `leads.scope_isolation` permits updating any lead the caller can see, and canon 28 gives `employee` `VIEW_DEPARTMENT_QUEUE` by ratified amendment — so an ordinary employee could move their whole department's pipeline. Marking a colleague's lead `won` is credit for a sale you did not make.
- **Remediation (applied):** `app.require_lead_handler(uuid)` holds the rule once, copied from the three RPCs that state it. `enforce_status_transition` calls it where `permission_key` is null on `leads`; `app.guard_lead_interaction_authority` calls it on `lead_interactions` (which closes SEC-1's last table by the same evidence). **Nothing became stricter than the RPC that walks it:** closure keeps `CLOSE_LEAD`, `assign_lead`'s `new->assigned` already carried `ASSIGN_LEAD`, and `process_lead_sla` is session-less and exempt.
- **The class, not the instance:** a null `permission_key` now means "apply this table's named fallback rule", and a table with neither a permission nor a fallback **FAILS CLOSED**. Only `leads` has nulls today, so the new branch is unreachable — which is the point: the next unguarded transition becomes a loud 42501 instead of a silent hole.
- **Test requirement (met):** `59_lead_handler_authority_test.sql` (14) — the colleague SEES the lead (positive control on the department queue), is then refused by direct DML *and* by the RPC, while the handler is permitted on the same lead and the same transition; ASSIGN_LEAD proven as the rule's other half; the closure path proven untouched; the system path proven still open; and "no table other than `leads` carries a null permission_key" pinned.
