# ENGINEERING_METHOD.md — ORVION Engineering Method

This document owns ORVION's engineering *method*: how a decision is classified and made, how a design is challenged, how a claim is measured, and the two verification protocols that are too long to belong in an operating kernel every session reads.

`AGENTS.md` remains the kernel and governs execution posture; it points here and is never overridden by this file. Every rule below is owner-ratified. The rules first ratified in `AGENTS.md` were relocated verbatim (2026-09-11, `SPEC-163`), so that routine execution stops paying for methodology it does not use; a rule added here since carries its own ratification date. Check 27 of `scripts/check_repository_consistency.ps1` fails if any anchor below stops existing here, so this authority cannot quietly become implicitly remembered.

**When to read which section.** An agent is routed here by `AGENTS.md`, and needs only the section its work triggers:

| Read this | When |
| --- | --- |
| §1 Standing execution directive | Starting any unit of work — phase, capability, slice, or migration |
| §2 Decision and architecture discipline | Classifying a capability, or making an architectural or owner-facing decision |
| §3 Measurement integrity | Writing or quoting any test, guard, or measurement |
| §4 Database verification protocol | The `DATABASE` verification profile applies |
| §5 Cross-path impact protocol | The `§5b` trigger list is touched |

## 1. Standing execution directive

**Standing execution directive (owner-ratified 2026-07-17): finish → audit → classify → execute.** (1) **Finish before proceeding** — no new unit (phase / capability / slice / migration) begins until the current one is complete on every axis: implemented, verified, tested, Review-Gate-passed, governance-satisfied, docs + Canon + repo synchronized, working tree clean, committed, no known in-unit debt. (2) **Pre-unit Critical Architecture Audit** — before each major unit, review as architect + auditor to *actively discover* missing structure / lookups / reference data / identifiers / relationships / FKs / indexes / constraints / events / drift / duplication; assume incomplete until proven otherwise; validate every conclusion against implementation, never against prior conclusions. (3) **Classify every decision immediately** — technical/architectural (derivable from implementation, PostgreSQL/Supabase, enterprise SaaS practice, current research) ⇒ decide, document the reasoning, continue; **business-policy** (customer/product behaviour, pricing, finance/compliance/legal, commercial strategy) ⇒ present options + trade-offs + recommendation and wait, never silently defer; insufficient evidence ⇒ research first, exhaust technical investigation before asking. (4) **Execution focus** — the active unit has priority; classify/record future improvements without pausing *unless* they are critical architectural debt, security, integrity, data-loss, or a structural defect that grows materially more expensive if postponed. This crystallizes conduct already owned in `AGENTS.md §2` and in §2–§3 below (Earn-It, Fundamental Domain Structure, discovery-to-guard `GOVERNANCE.md §18`, Learn-Before-Designing, definition-of-done `AGENTS.md §8`) — it restates none of them, it sequences them.

## 2. Decision and architecture discipline

**Governing meta-principle — Earn-It.** Optimize for engineering *confidence*, not process. Every step (and every artifact, document, and abstraction) must justify itself by measurably increasing confidence. If the same confidence is reachable with fewer steps or fewer files, prefer the simpler path. This guards against both governance bloat and documentation bloat.

**Four decision rules (owner-ratified 2026-10-08): LEARN BEFORE GUESSING → EARN IT → WORTH IT → SIMPLIFY IT WITHOUT WEAKENING.** They are applied in that order to every decision, small or significant. Their depth scales with the decision's risk and with how fast the facts change. None of them is a new gate or a separate research stage.

- **LEARN BEFORE GUESSING.** Before concluding, read what already answers the question:
  - the Canon and the ADRs;
  - the actual code and tests;
  - current Primary — read only; a write still needs its own Gate 2;
  - the relevant history in Git, the register and the CRs, including the history of each line a Step or Criterion will write (`git log -L`), read as it stands at `HEAD`: `SPEC-278` copied four manifest references from `SPEC-268` after `SPEC-270` had rewritten those lines, and was cancelled. What changed since a precedent is no substitute, because the precedent may already be stale: for a Draft copying `SPEC-278`, `git log <precedent>..HEAD` holds no `SPEC-270` commit. History is evidence, never authority; what can be pinned, the Gate enforces (`### Pre-Approval evidence sufficiency`);
  - for a fast-moving external API, SDK or tool, its current official documentation (`AGENTS.md §3` FRESHNESS).

  Then state a falsifiable hypothesis, with a positive and a negative control, and verify the effect rather than the intention. This is Learn-Before-Designing (stage 2 below) applied to every decision, not a second procedure. A routine choice needs a quick check; a major capability needs the fuller study that stage 2 describes.
- **EARN IT.** The governing meta-principle above: a change, step, file or rule must measurably raise confidence or remove a reproduced defect.
- **WORTH IT.** Weigh a real benefit against the cost and risk of obtaining it: blast radius, migration, a Primary gate, maintenance, and what the change forecloses. A real change that is not worth making now is recorded with an exact trigger instead (MONEY-3, CTRL-3), and is never dropped silently.
- **SIMPLIFY IT WITHOUT WEAKENING.** Take the smallest change that keeps every existing guarantee, and reuse an existing mechanism before adding one. Simplifying never deletes or relaxes a guard, a test, an owner-ratified rule or an evidence class: a simplification that weakens one is a regression.

**Fundamental Domain Structure vs Feature Implementation (owner-ratified 2026-07-17).** Earn-It's deferral pressure applies to *capabilities, infrastructure, integrations, workflows, automations, external systems, scheduled jobs, caches, optimizations, and feature behaviour* — not to the **canonical domain model**. A table, lookup family, enum, reference dataset, relationship, foreign key, constraint, index, event, canonical field, or business identifier that is an *inevitable* part of ORVION's domain belongs in the repository **now, even with no current consumer** — deferring it only forces an expensive structural migration after production begins, which ORVION exists to avoid. Include a structure now **only if it satisfies ALL of:** inevitable · architecturally correct · belongs to the canonical domain · reduces future structural migrations · improves long-term integrity · supported by modern enterprise best practice (as of the decision date). The decisive test: *"If ORVION were a mature enterprise travel SaaS in five years, would this structure almost certainly exist regardless of feature order?"* — if yes, add it in its correct canonical location; if it is speculative, feature-shaped, or has multiple equally-valid models whose correct choice depends on an unbuilt feature, do **not** invent it — record it with a trigger. Structural completeness is a first-class goal: future phases should primarily add *behaviour*, not redesign *structure*.

**Classify each capability at the start (this keeps reviews light):**
- **Routine** — established pattern, no architectural impact (a guarded RPC reusing a proven pattern). Minimal ceremony: phase-fit → design review → implement → Review Gate (with inline Excellence check). No Design Challenge.
- **Significant** — introduces or materially changes a business capability or architectural boundary (new/changed aggregate, phase/domain boundary, finance/security/identity-sensitive, hard to reverse, ADR-adjacent). Adds the Design Challenge and a fuller Excellence pass.
- **Owner-Decision** — changes long-term architecture or governance, or introduces a meaningful irreversible tradeoff. Act as the owner's **Technical Advisory Board (owner-ratified 2026-07-17)**: don't merely stop and request approval — explain *why* the decision exists, why it can't be objectively derived, whether it is reversible, and its assumptions; present *every realistic* option with a comparison across the axes that matter (architecture, operational model, scalability, implementation + operational complexity, maintainability, flexibility, vendor lock-in, migration cost, security, compliance, infrastructure, roadmap + ORVION fit); recommend one with evidence; and **teach the owner *how* to choose, not just what** — the goal is an informed decision, not a rubber stamp. Isolate the decision (design everything independent of it, per `AGENTS.md §1`), await approval, record an ADR. Prepare the analysis as a Decision Record first (precedent: `reports/history/google-offline-conversion-transport-decision-2026-07-17.md`).
  - **Every proposal — including the owner's — is evaluated, never auto-accepted (owner-ratified 2026-07-17): the owner proposes, repository evidence decides.** Each concludes as exactly one of **Adopt Now / Adopt Later (explicit trigger) / Reject (with evidence)**, judged by Earn-It + repository evidence + One-Authority + Test-before-trust + Learn-Before-Designing + stewardship.
  - **Permanent Engineering Review Board.** Review every non-trivial implementation through multiple standing perspectives that challenge one another before concluding — Repository Steward, Chief/Enterprise/Solution/Domain/Software/Database/Data/Integration/Security architect, Governance Custodian, Technical Auditor, QA, Systems Analyst, Technical Product Owner, Risk/Compliance/DevOps reviewer, Documentation Steward, Long-Term Maintenance engineer. Governance remains the final authority. (This is the Excellence Check's multi-role lens, stage 6 below, widened to architectural roles — not a separate gate.)

**Workflow stages:**
1. **Phase-fit + Earn-It → classify tier.** ("Does this belong to the current phase, or am I solving a future problem?")
2. **Research when it materially helps (Learn-Before-Designing).** Use current external evidence as a lightweight Design Review tool whenever it would measurably improve a decision — validating a current best practice, evolving external-platform behaviour, an official spec, or an assumption before implementation. Scale it to the decision: a quick check for a routine choice touching a fast-moving external surface; for a *major* capability (UI, AI, communications, reporting, automation, analytics, search, integrations), a fuller study of the strongest current implementations — why they work, why users prefer them, where they fail, what to adopt vs deliberately avoid. Verify against up-to-date official sources (the ecosystem moves fast). When a fast-moving surface is in play — SDKs, APIs, AI tooling, cloud/infrastructure, external-platform behaviour — **prefer verifying current official information over relying on historical/stored knowledge**, because stored knowledge goes stale silently and a wrong assumption there is expensive. Goal: strengthen engineering judgment with evidence, not replace it — and not research every task. The same discipline governs small decisions as LEARN BEFORE GUESSING (above), at a depth scaled to their risk; it is this stage applied everywhere, not a second procedure.
3. **Design Review** — gather the minimum context, then confirm canonical fit: read *only* the relevant canonical docs and the *required* schema/migrations for this capability, and look for an existing precedent (an RPC or pattern already in the repo) to reuse rather than re-invent. Minimal, precedent-first reading is what keeps a capability both correct and cheap.
4. **Design Challenge** — *Significant only.* Objective: can we reasonably demonstrate the selected solution is the strongest practical solution among realistic alternatives? Adversarial sweep for what is MISSING or SIMPLER/BETTER (relationships, business concepts, catalog values, events, permissions, validations, integration points, hidden assumptions, simplification). Output = short findings list resolving to one of three engineering outcomes — reject, improve, or confirm the approach — then implement; a question to the owner is *not* an outcome, and is warranted only if the sweep surfaces a genuine architectural conflict (a stop condition). A full written report only at phase/gate boundaries.
5. **Implement + prove** — clean `db reset`, behavioral tests, smoke-test, Database Audit (for schema work).
5b. Cross-path impact sweep — mandatory when triggered; the full active rule is §5 below.
6. **Review Gate + Excellence Check** — the CR Review Gate PLUS six questions: (a) anything overlooked? (b) simpler equivalent? (c) unnecessary complexity introduced? (d) reusable business concept emerged? (e) negligible-cost future-debt avoidance? (f) **multi-role usability** — reviewing not only as an architect but through the affected operational roles (sales, reservations, finance, accountant, call-center, support, marketing, operations, owner, plus the engineering roles): can each perform their workflow naturally? A capability no real role can use naturally is incomplete. In-phase improvement → implement; future → record at its trigger.
7. **Complete** — autonomous per `AGENTS.md §2` when verified and no new decision; sync manifest/ADR; commit; push.
8. **Phase-transition checkpoint** — execute a whole roadmap phase capability-by-capability without stopping, then pause at phase end with a concise checkpoint: what was completed, findings, deferred items + triggers, architectural health, next phase, recommendation, any observation deserving owner attention. Then begin the next phase.

Governance is self-revising: if a step stops earning its confidence, propose simplifying it; if a missing practice would raise quality without materially slowing execution, propose adding it. Reconsider methodology only on concrete repository evidence, never on preference alone.

### Pre-Approval evidence sufficiency

Approval freezes authority, so the evidence that makes execution safe must be sufficient *before* the freeze, not discovered during it. Three failed Slice-12 successors proved the asymmetry: execution-time guards failed closed correctly, while the frozen contracts themselves were not always evidence-closed (`SPEC-196`).

A Change Request carries a bounded `## Pre-Approval Evidence` section whose every predicate resolves to exactly one of three values. There is no score and no compensation between predicates:

- **PASS** — every required predicate is satisfied.
- **FAIL** — a required predicate is contradicted by evidence.
- **INDETERMINATE** — required evidence is missing, stale, malformed, or unresolved.

`FAIL` and `INDETERMINATE` both block the transition they govern; only `PASS` permits it. `INDETERMINATE` is a first-class outcome rather than a soft pass, because "we did not look" and "we looked and it is fine" are different facts.

Four evidence classes are required where deterministically applicable:

- **Consumer Closure** — for each changed fact or surface, the relevant consumers and a disposition of `WRITE`, `VERIFY`, or `UNAFFECTED`, with evidence. This closes *what depends on the changed fact*, which is a different question from Write Scope's *what may be modified*. An `UNKNOWN` disposition or a named unresolved material consumer is `INDETERMINATE`.
- **Execution-Boundary Satisfiability** — a frozen sequence must be possible. Declared invariants are checked against the four bounded checkpoints `BEFORE_IMPLEMENTATION`, `BEFORE_IRREVERSIBLE_ACTION`, `AFTER_IRREVERSIBLE_ACTION`, and `BEFORE_COMPLETION`. An invariant required green at a mandatory boundary that lies inside its own declared red window is `FAIL`. This is bounded checkpoint comparison, never simulation of arbitrary program state.
- **Permanent-Control Admission** — a new permanent control freezes its reuse assessment, the distinct property it adds, a reproduced causal negative, positive and negative test designs, a non-empty-population obligation, and a mutation obligation. Actual positive, negative, population, and mutation proof is supplied after implementation, by the certified suite, and is never asserted before the code exists.
- **SPEC Identity Allocation** — the proposed identity must be legally allocated. `CR_LIFECYCLE.md` §4 owns that rule.

Applicability is derived from repository evidence — Write Scope, derived verification profiles, known control and governance surfaces, cross-path triggers, and declared irreversible actions — never from the contract's own `Change Class` label. A declared class is descriptive input; it can add obligations but can never remove one that repository evidence makes applicable. An exemption that cannot be derived deterministically is `INDETERMINATE`.

**Derivation is per predicate (2026-09-20, `SPEC-210`).** "Where deterministically applicable" is a statement about each class, not about the contract. Deriving it once — *did this change reach a special surface* — and then asserting that single answer about three different questions was wrong in both directions, and both were reproduced against the evaluator before it was changed. A governance-prose contract that adds no permanent control was refused for honestly declining `Permanent-Control Admission`, with a message claiming repository evidence made it applicable when none had been consulted for that predicate. In the other direction, `scripts/parity_surface.sql` decides what the structural parity detector *measures* and is neither a control path nor a profile trigger, so `SPEC-207` changed it, wrote 68 lines of Pre-Approval Evidence, and the evaluator returned `NOT APPLICABLE` without reading one of them. `Permanent-Control Admission` is now derived from whether Write Scope reaches a surface where a control that runs forever lives; `Consumer Closure` and `Execution-Boundary Satisfiability` follow the contract-level trigger, which now also covers the verification, generation and publication authorities that no profile marks. Volunteering a predicate the repository does not derive is always legal and binds fully — a label adds, never removes.

**Verification write closure is derived, not discovered (2026-09-20, `SPEC-210`).** A mandatory verification that *regenerates a tracked artifact and byte-compares it* makes that artifact part of the contract's write surface whether the contract planned to touch it or not: `Invoke-Verification` treats any non-zero exit as fatal, and a frozen `Write Scope` cannot be widened afterwards. `SPEC-203` carried `ai-map.json` but not `reports/master/MASTER_API_CONTRACT.md`, deployed to Primary, and only then met mandatory Check L3 — the repair lay in a file its own frozen scope forbade, so an irreversible action had already happened by the time the contract was cancelled. `SPEC-205` died to the same shape. The two closures this repository currently owns — the manifest's `ai-map.json` (Check 7) and `supabase/migrations/`'s `MASTER_API_CONTRACT.md` (Check L3) — are refused at Approval rather than at `-Finish`, and the rule is skipped when the artifact does not exist, so retiring one needs no edit.

**Assurance is enforced by the Gate, not by the reader (2026-10-14, `SPEC-281`).** The owner's four assurance responsibilities are predicates inside this evaluator, never four gates, and none depends on an agent having read this page:
- **CAG, admission.** One definition of a contract's transitions is judged by the hook against `HEAD` and by CI at every commit of a range, so `git commit --no-verify` changes nothing CI admits; before this, four transitions the hook refused were READY in CI. At Approval the Gate also prints `CRITERIA`: how many criteria it will verify at Complete, and how many are left to Review.
- **ACI, authority change impact.** Changing a line `GOVERNANCE.md` §6 pins is an authority change. Its Consumer Closure names every live file that names the line, which the Gate finds itself with `git grep` at the base, leaving out terminal contracts and dated reports. The commit that moves a pin is judged the same way, so omitting the declaration does not avoid it.
- **SACI, stale authority.** A pinned line holds exactly its ratified text in every state, whatever Write Scope allows (`PINNED_AUTHORITY_CHANGED`). A step that names one gives it a disposition: `UNAFFECTED` or `VERIFY` to read it, and `WRITE` only beside a change to its pin.
- **PICF, completion feasibility.** An Acceptance Criterion may carry `check:` clauses (`changes/TEMPLATE.md`). At Approval a check that can never hold is `FAIL`: a file outside Write Scope that already disagrees, a pinned line, a commit outside the contract's history, or two checks no final state satisfies together. At Complete every check must hold in the completing tree, locally and in CI.

What stays judgment: whether a disposition is true, whether a criterion without a check is met, and any contradiction written as neither a check nor a pin. `-Gate -Trusted` judges a candidate with an evaluator from outside it, and `scripts/promote_main.ps1` binds that judgment to the one SHA it pushes; whether `main` can move without them is GitHub configuration and credential separation the repository cannot set (`CTRL-19`).

**Reduce uncertainty before freezing: sandbox and prototype (2026-10-13, owner directive).** Approval freezes authority, so when uncertainty about a Draft is material, test the design before approval rather than discover a preventable defect while executing it. This is risk-based, never mandatory. A *sandbox* is an isolated, disposable environment, such as a scratch directory, a fresh clone (not a `git worktree`, which shares the repository's refs and config), a separate local Supabase project id and ports, a throwaway container, or the control suite's own sandbox bootstrap. It is used to reproduce a defect, compare alternatives, or test an assumption about runtime, database, CI or governance behaviour. A *prototype* is the smallest disposable version of the intended change, run in a sandbox. It shows whether the repair works, exercises its positive and negative cases, and reveals the exact files, consumers and blockers, so that the Draft's Write Scope, steps, criteria and Pre-Approval Evidence are written from observation rather than prediction. Three rehearsals cover the failures that cancelled recent contracts:
  - run the pinned toolchain against a disposable project and the affected suites (`SPEC-271` met a CLI regression only at execution);
  - commit the Draft's whole lifecycle in a disposable clone and run `-Gate -BaseRef origin/main` over the future publication range (`SPEC-272`'s scope could not publish its cancelled predecessor);
  - check each Acceptance Criterion and the approval transition against the prototype's actual result (`SPEC-200`, `SPEC-252` and `SPEC-254` froze criteria that were false as written).

  Use them only when they cost less than a failed contract; a typo or an already-proven deterministic correction needs neither. Changing a disposable environment is not a write to the repository, and it confers no authority. A disposable clone may hold temporary commits when range, CI or lifecycle behaviour cannot be reproduced otherwise. Disable its push URL first (`git remote set-url --push origin none`): those commits are never pushed, merged or promoted, and never count as certified implementation. A sandbox never touches the authoritative working tree or its Git refs, Primary, production systems, existing local databases, shared containers, credentials, or other agents' work. Measuring the commands a contract will be judged by remains §3's rule ("Measure a verification before you freeze it as mandatory"), unchanged; where running one would disturb shared state, a sandbox lets an author run it in isolation. A prototype informs the contract and never replaces its frozen verification. `PROJECT_CONTEXT.md` §8 excludes experiments that bypass the canonical guidance; this one serves a contract under it.

## 3. Measurement integrity

- **No vacuous security tests (owner-ratified 2026-08-27).** *A test that can pass with zero affected rows is not an earned security test.* This has now bitten the repository twice: a denial assertion whose fixture was empty, and — during WP-03 — a proof-upload test that ran as `employee`, whose `insert … select … from public.subscriptions` read **zero rows** because `employee` lacks `VIEW_SUBSCRIPTION_STATUS`, so it inserted nothing and `lives_ok` reported success. Every authorization or security test must therefore, in order: establish the positive fixture; prove the actor genuinely **holds** the capability under test; prove the target row is **visible** where visibility is expected; perform the **positive** operation and assert it changed something; only then perform the negative operation; and assert the **exact** error code or a row count that could not have been produced by an empty query. When an assertion rests on `lives_ok`/`throws_ok` over an `INSERT … SELECT` or a filtered `UPDATE`, add a companion assertion that the row now exists (or the count changed) — "it did not throw" is not evidence that a write occurred.
- **A green guard proves only the property it actually measures.** Before quoting one, read what it reads. If a guard's description is stronger than its measurement, **fix the guard** — that is the finding, and it is recorded in the register as a first-class one, never as a footnote. **A stubbed command is not the command (2026-09-20).** The control suite replaces the profile verifications with fixtures, which proves *the orchestrator invokes X and treats its exit code correctly* and proves nothing whatever about whether X can succeed. Assertion 103 asserted that "a DATABASE change whose whole protocol succeeds reaches `LOCAL_CERTIFY: READY`" over a parity command stubbed to `exit 0`, and stayed green across nineteen contracts while the real command was structurally incapable of ever returning 0 (`PAR-6`). Both claims are legitimate; they are different claims, and an assertion must name the one it measures.
- **Measure a verification before you freeze it as mandatory.** Run every command the contract will be judged by — the ones its profile makes mandatory as much as the ones it names in `Additional Verification` — and record the exit code it actually returned. `SPEC-205` froze `scripts/check_database_parity.ps1` in a frozen section, for a correct reason, without ever running it; it cannot return 0 bare, `Invoke-Verification` treats that as fatal, and a frozen section cannot be corrected in place, so the contract was cancelled. This is the one satisfiability class that is *not* mechanically derivable at Approval — nothing short of executing the command establishes it — which is exactly why it is a standing obligation on the author rather than a gate.
- **Attack every new detector with a counterexample before trusting it**, in both directions: construct a case it must flag and one it must not. A guard that can be satisfied without satisfying its invariant is the class the discovery-to-guard loop exists to eliminate. Prove enforcers by **defect injection** — inside a savepoint, drop the named enforcer, assert the violation *succeeds*, roll back, assert it is refused again (the **PAR-4** pattern in tests 70/72/73/76). "It did not throw" is not evidence that anything was enforced.
- **Static analysis is a lead, never a verdict.** It cannot see trigger arguments (**MEAS-1**), values assembled at runtime, RLS visibility, or whether a fixture row exists at all — a static pre-check reported "zero divergence" over ten impossible fixture rows (**TEST-65**). Prove fixtures valid by observing them, not by matching their shape.
- **Test both doors.** Where direct DML is reachable, an RPC-only check is a half-fix: `authenticated` holds table writes, so PostgREST exposes the table beside the RPC (**BOOK-1**, **ADMIN-1**, **FIN-8**, **FIN-10**, **QUO-1**). Prove positive and negative controls *independently* — verify the actor genuinely holds the capability and can see the row before asserting that anything was denied.
- **A failed run is not automatically a finding.** Distinguish infrastructure from product: Docker down, containers still restarting, or a probe running under the session a previous assertion left behind look identical to a real defect in a transcript, and each has already been mistaken for one. Establish which it is before recording anything.
- **A harness result is evidence only after every participant's own output is read (2026-10-13, `SPEC-278`).** A race, an injection or a mutant is judged by the raw output of each session and by a final state the scenario implies, never by the attacking session's line alone. Slice 42's first race printed `B waited 0s; UPDATE 1` while session A had failed and posted nothing, so nothing had been raced; the same session took a `git worktree` for a sandbox, which §2 forbids. Three traps followed, each an assumption a read would have caught: a bare `journal_entries` header is refused at COMMIT by the deferred balance check, so a fixture posts its header and balanced lines in one transaction; append-only rows cannot be cleaned up, so a rerun uses fresh ids instead of deleting the last run's; and an injection leaves the weakened object installed until it is restored from source and the restoration proven.
- **No exemption is ever manufactured to make a guard pass**, and no budget is ever raised to make a document fit (Check 5 has been tripped repeatedly; the answer has always been to trim). Fix the subject, or record why the guard is right and the work is wrong.
- **Every discovered finding ends in exactly one declared state** — *FIXED and behaviourally verified* · *PROVEN INTENTIONAL* (or proven not a defect, by experiment rather than by inspection) · *UNPROVEN* · *OWNER DECISION REQUIRED* — and an owner decision is legitimate only after canon, the SSOT/register, schema, implementation, consumers, tests, runtime, Primary and authoritative external documentation have been exhausted **in that order**. Never silently abandon a finding, and never hide an open question to make a package look complete.
- **External credentials never pass through the agent.** A secret for a third-party system (a database role password, an OAuth client secret, an API key, a token) — Phase 8's `orvion_integration` password and n8n/Google OAuth client secret are the precedent — is entered by the owner directly into its destination (the database console, n8n's credential UI, the provider's own form), never into a prompt, tool call, file, or any other agent-visible surface. An agent must not generate, request, echo, or transit such a secret, even transiently in a tool call whose output only the agent sees. Concrete application of `CODING_STANDARDS.md §8`; verify by effect (a credential test passing, a query succeeding), never by inspecting the secret.
- **Quote only what a log printed (owner directive 2026-10-09).** A count, a verdict or a duration is copied from the output that produced it, never recalled, predicted or rounded into a claim. A progress report once carried a "289 passed" line that no run had printed, and it had to be retracted. While a run is still going, say that it is still going.
- **A timing is evidence only with its conditions.** Record the command, its scope, the environment and what else was running; `scripts/run_timed.ps1` writes all of them into the run's START line. A run measured beside other work is labelled as such and is never a baseline: `SPEC-248`'s 50.3-minute `-Finish` ran beside a validation suite. An estimate or a remembered duration is never presented as a measurement.
- **Every run is timed, a long run is watched, and the watcher decides nothing (`SPEC-283`).** An agent starts every repository verification it runs itself - `-Finish`, and any `scripts/test_*`, `check_*` or `verify_*` suite - through `scripts/run_timed.ps1`, and follows a run longer than a few minutes with `scripts/watch_run.ps1` while it runs: the runner blocks until its command ends, so the watcher is started at the same time, from a second shell or the agent's background monitor, and waits for the log if the run has not started; started after the runner returns, it only replays a finished log, with no heartbeat or estimate while the run was going; `-Finish` refuses any other start. `check_agent_continuity.ps1` times every run itself, so the pre-commit hook, CI and the owner's promoter are timed as well, and appends each run nobody timed to the one timing history the watcher keeps, outside the repository (CI's own timings stay on GitHub). `scripts/watch_run.ps1` follows a `run_timed.ps1` log, records every test line a suite prints and every evaluator stage with its own time, and reports every result line; a heartbeat naming the stage that is running whenever output stops, with the time left estimated from comparable successful runs, or no estimate below two; and a runner that died without finishing. Its findings are evidence labelled by what supports them: `[confirmed]` for a failure that also failed in earlier runs, `[hypothesis]` for a repeated command, a slow step or run, or a step recent successful runs had and this one lacks. An agent's monitor follows a run with `-Brief`, which prints only failures, findings, heartbeats, a progress line and the end, so a passing run costs a few notifications. `-Report` summarises the history: where the time goes, the slowest tests and stages, regressions, and failures ranked by their rate per run of the same name. An agent acts on a finding only through the lifecycle, tells the owner of one that needs the owner through its own client's notification, and never presents a local log as a notification; a Skill, Guard or Hook a finding suggests is a candidate for the Improvement Loop, never a change. `scripts/watch_ci.ps1` judges the runs on one exact SHA and branch against that branch's own contract, derived by the deriver `-Certify` uses, and reports the failed job, step and error lines; a check that never ran is reported MISSING, never as passed. A familiar message is never a cause: one Migration CI log held a harmless `toomanyrequests` beside the fatal `Bus error`. So the cause is established from the evidence before anything is rerun, and a mandatory verification is never skipped because a watcher once saw it pass. `scripts/watch_selftest.ps1` proves both watchers whenever either changes, and with `-Live` replays six real runs.
- **Nothing open is lost (owner-ratified 2026-10-12).** Chat memory, an agent's memory and a session report are conveniences, never the place an open obligation lives. Before a task is complete, and before a session stops, every new item goes to the one home `GOVERNANCE.md` §2 assigns it:
  - a defect goes to the register with its evidence;
  - an accepted engineering decision goes to its ADR or Canon;
  - an owner-approved business requirement goes to Canon, through a Change Request;
  - a decision the owner has not made goes to the register, with its decider, its proposed default and `PROPOSED` in its status, so Check 25 puts it on the manifest's boot line. Nothing two agents agreed on is ever recorded as the owner's decision;
  - an idea not yet worth building goes to `reports/future-backlog.md`, with its trigger;
  - a rejected or superseded proposal keeps its disposition where it was proposed (`GOVERNANCE.md` §3), so it is never mistaken for live work;
  - work in progress goes to the active contract's Runtime Checkpoint.

  Every open register finding, surface and decision then needs one row in the Action registry of `MASTER_EXECUTION_PLAN.md`, in the same change. That row gives its class, its decider, its latest safe boundary and its treatment. Check 29 refuses the change otherwise, and fails when a boundary is crossed with its items still open, so reconciliation is part of every guard run rather than a step to remember. The owner's lifecycle maps onto the existing one and adds no second state machine:
  - LEARN and VERIFY are FRESHNESS and PRECHECK;
  - DECIDE is §2;
  - IMPLEMENT, TEST, REVIEW and COMPLETE are EXECUTE, VERIFY, the Review Gate and `-Finish`;
  - RECONCILE and PRESERVE are this rule, the registry check, and the durable checkpoint test of `AGENTS.md` §2.
- **A lesson is promoted, never only remembered.** At each phase boundary, a lesson an agent learned that a future session needs moves to the authority that owns its subject — a PowerShell trap to `CODING_STANDARDS.md §12`, a lifecycle rule to `CR_LIFECYCLE.md`, a measurement rule here — through the next Change Request that can carry it. Agent memory may point at the repository; it is never the only place a lesson lives.

## 4. Database verification protocol

For database work, do not narrow this protocol: fetch and verify target; clean `npx supabase db reset`; pgTAP Pass A; all relevant HTTP suites; pgTAP Pass B without reset; smoke via `docker exec -i supabase_db_ORVION psql -U postgres -d postgres -f - < scripts/verify_database.sql`; read Primary ledger, function hash, and `_combined` structure hash independently from Primary **and record all three in `reports/evidence/primary-ledger-evidence.json`, which a contract that deploys must therefore carry in its Write Scope**; run `scripts/check_database_parity_evidence.ps1`; run repository consistency; regenerate owned artifacts. Match counts and results, not remembered numbers. Primary for this repo is only ref `vrvtsxexkiiiivlkdxzp`; Secondary belongs to another repo and must never receive this repository's deployment. Confirm the target in `MASTER_INTEGRATION_CATALOG.md §0` before schema-changing/destructive calls.

Every command above is destructive, slow, or needs a running stack, so none runs automatically inside a Gate. `scripts/check_agent_continuity.ps1 -Finish` executes that protocol — and only `-Finish` does, never `-Boot` or `-Gate`. pgTAP runs on both sides of the HTTP suites deliberately: Pass A proves the migrations' own invariants on a clean database, Pass B re-proves them after the suites have written through the API, and only Pass B can catch a suite that corrupts state. Two things the protocol cannot derive must therefore be declared, and both are refused at Boot if missing: the `supabase-local` capability (`DATABASE_CAPABILITY_NOT_DECLARED`), and which `scripts/verify_*` HTTP suites are relevant, named in the contract's Additional Verification (`DATABASE_HTTP_SUITE_NOT_NAMED`). A command that cannot run is a named failure with an exit code, never a standing excuse; "could not execute" still never becomes green. Declaring `supabase-primary` additionally makes `scripts/check_primary_ledger.ps1` mandatory, which is what separates a declared connector from proven recorded evidence — it is attributable and current, and it is still not a live read. **`-Finish` cannot read Primary** — there is no local credential and `AGENTS.md` keeps credentials out of Git — so the parity step it executes is `scripts/check_database_parity_evidence.ps1`: it validates that record (attributable, internally self-consistent, naming Primary rather than Secondary, belonging to this history, carrying both surface hashes) and then runs the one parity engine, `scripts/check_database_parity.ps1`, against the recorded values, propagating its exit code exactly. Parity stays MANDATORY and stays fail-closed; what moved is only where the three values come from. The live read remains an agent action at the execution boundary, and a stale record is caught causally rather than by a clock: change the repository and the local database it generates moves, so the recorded Primary values no longer match (`PAR-6`).

## 5. Cross-path impact protocol

When changing triggers, RLS, grants, SECURITY DEFINER functions, lifecycle/archive/catalog enforcement, events, immutable fields, scope, FK/key shape, permissions, vocabulary, columns, constraints, authorization helpers, or attribution structures, answer both: (1) which existing execution paths now meet the new rule, and (2) which code consumes/parses/derives from the changed structure. Use `scripts/impact.ps1 -Target <name>`. Classify interactive, multi-tenant system, batch/set-based, scheduled, integration, and administrative paths and prove each affected class. Restricted/ineligible tenants must be skipped by system paths without weakening the final gate; interactive callers must still receive intended errors.
